# SplatSim Pipeline — Concrete Walkthrough (read against the cloned repo)

This document is grounded in the actual code under `sim2real_vision/SplatSim/`.
Every claim has a file pointer so you can verify it before doing anything.
Where SplatSim's design assumes UR5 + PyBullet but you have Kinova Gen3 + mjlab,
that delta is called out in **[Kinova-delta]** notes.

The repo contains *two* generations of the same idea:

- `splatsim/robots/sim_robot_pybullet_splat*.py` — the original CoRL-24 path,
  with hard-coded paths and bespoke per-task forks. **Treat as reference, not
  template.**
- `splatsim/robots/sim_robot_pybullet_base.py` + `..._object_on_plate.py` — the
  cleaned-up path the README points at. This is what we'll build on.

The renderer comes from
`submodules/gaussian-splatting-wrapper/gaussian_splatting/` — the INRIA 3DGS
reference rasterizer (`gaussian_renderer.render`, `GaussianModel`).

Key design choice: there is **no** parallelization. SplatSim runs a single
PyBullet env, single GPU 3DGS render per frame. Throughput is on the order of
tens of Hz, not thousands. Demo data is **scripted/teleoperated**, not
generated by RL roll-outs. This is fundamentally different from your current
GPU-parallel mjlab DAgger setup. **[Kinova-delta]** addresses this in §6.

## 2. Stage A — Asset preparation (one-shot, off-line)

### A.1 Capture and 3DGS training of the *robot+background scene*

README §"Adding a new robot" prescribes:

1. Park the robot in a known, easy-to-describe pose (all 90° joint angles
   recommended). Record those joint angles — they become `joint_states` in
   `configs/object_configs/objects.yaml`.
2. 1–2 min phone video, all angles, diffuse light, textured background.
3. Convert to `~/data/<robot_name>/input/*.jpeg`.
4. COLMAP: `python submodules/gaussian-splatting-wrapper/gaussian_splatting/convert.py -s ~/data/<robot_name>` →
   produces sparse SfM in `~/data/<robot_name>/sparse/0/`.
5. Train 3DGS: `python submodules/.../gaussian_splatting/train.py -s ~/data/<robot_name>` →
   produces `output/<id>/point_cloud/iteration_30000/point_cloud.ply`.

The COLMAP camera intrinsics/extrinsics from this dataset are reused
**verbatim** at runtime as the static "base camera" (see `setup_camera_from_dataset`,
`sim_robot_pybullet_base.py:882`). This is why the captured-camera viewpoints
implicitly become the deployment camera viewpoints unless you add new ones.

### A.2 Capture and 3DGS training of *each manipuland*

Same procedure, but per object. Configs in `configs/object_configs/objects.yaml`
have one block per object (apple, banana, plate, T-block...). Each object
gets:

- `ply_path`: path to its trained `point_cloud.ply`
- `transformation.matrix`: 4×4 splat→canonical-frame transform (set in A.4)
- `aabb.bounding_box`: tight 3D box in the splat's own frame, used at runtime
  to crop out background contamination (see `transform_object` in
  `splatsim/utils/robot_splat_render_utils.py:101`)

### A.3 Per-link Gaussian segmentation (KNN approach)

Run `python scripts/articulated_robot_pipeline.py --robot_name <name>`
(`SplatSim/scripts/articulated_robot_pipeline.py`).

What it does, line-by-line:

```
articulated_robot_pipeline.py
─────────────────────────────
  load gaussians.ply             (line 86–95)
  load URDF in PyBullet          (line 97–119) — set joints to scan pose
  for each link L:
    hide all other links
    render 9 PyBullet point clouds (front/back/left/right/top/bottom + 3 oblique)
    via splatsim/utils/cameras.py::get_overall_pcd
    label every point with link-id L                            (line 130–143)
  X = concat(all_link_pcds), y = concat(labels)
  knn = KNeighborsClassifier(n_neighbors=10).fit(X, y)          (line 160)
  apply objects.yaml::transformation to splat_xyz               (line 187–197)
  filter by AABB                                                (line 200–238)
  splat_labels = knn.predict(splat_xyz)                         (line 243)
  save → data/labels_path/<robot_name>_labels.npy               (line 267)
```

Output artifact you must commit/track: `data/labels_path/<robot>_labels.npy`
— a 1-D array of size `N_gaussians_in_AABB` mapping each robot-Gaussian to
a PyBullet link index.

### A.4 Splat ↔ simulator alignment (manual, ICP in CloudCompare)

The trained 3DGS lives in **COLMAP world frame** (arbitrary scale, arbitrary
orientation). The PyBullet simulator lives in its own metric world frame.
You need a 4×4 `T_robot_to_splat` that maps PyBullet world points into the
3DGS world.

The README mandates a manual workflow:

1. Open both `data/pcds_path/<robot>_pcd.ply` (the PyBullet point cloud
   from A.3) and the trained 3DGS `.ply` in CloudCompare.
2. Crop the splat down to the robot.
3. ICP the splat onto the PyBullet pcd: first w/o scale, then nudge by hand,
   then ICP w/ scale.
4. Copy the 4×4 from `Properties → Transformation History` into
   `configs/object_configs/objects.yaml::<robot>::transformation::matrix`.
5. Re-run `articulated_robot_pipeline.py` — the second viz should show
   color-coded links matching the splat.

This step is the **highest-friction part of SplatSim**. It is per-scene
manual work; there is no automated path.

## 3. Stage B — Online runtime (the per-step render loop)

This is the core algorithmic content. It runs in
`PybulletRobotServerBase` (`sim_robot_pybullet_base.py`).

### B.1 Process topology

```
Terminal 1 (server, holds GPU + PyBullet):
  python scripts/launch_nodes.py --robot sim_ur_pybullet_apple_interactive \
                                 --robot_name <robot>
   │
   └─► launch_nodes.py:104 instantiates AppleOnPlatePybulletRobotServer
       (subclass of ObjectOnPlatePybulletRobotServer → PybulletRobotServerBase)
       Calls server.serve() — main loop, see §B.4

Terminal 2 (client, drives the agent loop):
  python scripts/run_env_sim.py --agent <gello|replay_trajectory_and_save|...>
   │
   └─► run_env_sim.py:62 ZMQClientRobot at port 6001 → calls into server
       Steady-state loop: run_env_sim.py:313–368
         action = agent.act(obs)
         obs = env.step(action)   # this does the ZMQ round-trip
```

ZMQ method dispatch is in `sim_robot_pybullet_base.py:64–114`:
- `command_joint_state(joint_state)`
- `get_joint_state()`
- `get_observations()` ← this is where the splat render happens
- `set_object_pose(...)` ← used by replay agent to teleport objects

### B.2 Per-frame physics + render flow

Every time the client calls `get_observations()`:

```
PybulletRobotServerBase.get_observations()    sim_robot_pybullet_base.py:915
│
├─ poll PyBullet joint state, ee pose, obj poses
│
├─ if any camera enabled:

│     │   robot_uid, initial_link_states)
│     │     → for each link L: compute (R_rel, t) from
│     │        T_link_initial⁻¹ · T_link_now (in PyBullet world)
│     │
```

### B.3 The math, in two equations

Per-link rigid update of the robot Gaussians (means):
```
   xyz_world_i  = R_rel_L · xyz_world_initial_i + t_L     (for i ∈ link L)
   xyz_splat_i  = T_robot_to_splat⁻¹ · xyz_world_i
```
`R_rel_L`, `t_L` come from PyBullet FK relative to the snapshot pose
captured during scanning (see `compute_transformation` at
`splatsim/utils/utils_fk.py:40`).

Covariances/SH must rotate too — the SH rotation uses Wigner-D matrices
on bands l=1,2,3 (`transform_shs`,
`splatsim/utils/robot_splat_render_utils.py:160`). This is what keeps
view-dependent shading consistent under joint motion.

Per-object (rigid body) update — `transform_object`,
`splatsim/utils/robot_splat_render_utils.py:101`:
```
   xyz_canon = R_canon · xyz_obj + t_canon          (object .ply → canon frame)
   xyz_splat = T_robot_to_splat⁻¹ · (R_pose · xyz_canon + t_pose)
```
where `(R_pose, t_pose)` is the object's PyBullet world pose.

### B.4 Two server loop modes (`SERVE_MODES`)

Defined in `PybulletRobotServerBase` (sim_robot_pybullet_base.py:151):

- `INTERACTIVE`: just step physics, respond to ZMQ commands. Used for
  teleop, replay, and policy deployment.
- `GENERATE_DEMOS`: also runs `serve_loop` from
  `sim_robot_pybullet_object_on_plate.py:225` — randomizes object pose, runs
  a scripted plan-and-grasp pipeline (`plan_given_this_state` in
  `..._object_on_plate.py:30`), and dumps obs pickles to disk.

The **scripted-demo path** is the one that produces SplatSim's training data.
It uses `plan_joint_motion` (PyBullet RRT) + a hand-tuned
`GRASP_CONFIGS` table (`sim_robot_pybullet_base.py:156–...`) that has one 4×4
grasp pose per object class (apple, banana, orange, T-block). **There is no RL.**

## 4. Stage C — Demo collection

Three options, in increasing effort:

| Mode | How to invoke | What you get |
|------|---------------|--------------|
| Scripted plan-and-grasp | `launch_nodes --robot sim_ur_pybullet_apple` (note: NOT `_interactive`) → server runs `serve_loop` w/ `GENERATE_DEMOS` mode in a tight loop, writing `{traj_folder}/NNN/*.pkl` until `MAX_TRAJECTORY_COUNT` (default 500). | Cheapest. Limited to whatever `plan_given_this_state` supports (pick → drop on plate). |
| Replay recorded | `launch_nodes --robot sim_ur_pybullet_apple_interactive` then `run_env_sim --agent replay_trajectory_and_save` → `ReplayTrajectoryAgent` (`splatsim/agents/replay_trajectory_agent.py`) reads existing `.pkl`s back, sets object poses, drives joints, and dumps rendered PNGs to `{traj}/NNN/images_1/`. | Used to *re-render* old trajectories with a new splat / new camera. |
| GELLO teleop | same `_interactive` server + `run_env_sim --agent gello --use-save-interface` (`splatsim/agents/gello_agent.py`). Press `s`/`q` in the gray window to start/stop a recording. | Only path for tasks SplatSim doesn't have a planner for. |

`save_frame` from `gello.data_utils.format_obs` writes one pickle per
control step. Each pickle holds: `joint_positions`, `joint_velocities`,
`ee_pos_quat`, `state`, `action`, `<obj>_position`, `<obj>_orientation`,
`base_rgb` (a torch tensor [3,H,W]), `wrist_rgb`, `gripper_position`.

Critical detail: **images are stored as torch tensors inside the pickle**
(see how `replay_trajectory_agent.py:91–97` decodes them with `.detach().cpu()
.numpy()`). This is small per-frame but big per-trajectory; budget disk.

## 5. Stage D — Policy training and deployment

### D.1 Training (SplatSim does NOT do this in-repo)

The `policy_agent.py:138` `ckpt_path` is a hard-coded absolute path inside
the *external* `diffusion_policy` repo (Chi et al., RSS 2023). Training is
out-of-tree:

```
demos in {traj_folder}                           ← produced in Stage C
  │
  └─► converted to a Zarr/h5 dataset by diffusion_policy's data tooling
      (the format expects keys like camera_1, camera_2, robot_eef_pose, action)
      │
      └─► python diffusion_policy/train.py task=...image_real_image
          → checkpoint .ckpt
```

The `policy_agent.py:196 act()` shows the inference contract:
- Input: `obs_dict_1 = {camera_1: <wrist tensor>, camera_2: <base tensor>,
  robot_eef_pose: <state>}`, with a sliding 2-frame stack.
- Output: a 16-step action chunk; the agent steps through it action-by-action,
  re-querying when consumed (line 280–309).
- Action space: end-effector (x,y) target + IK-ed back to joint angles,
  fixed orientation (`self.correct_ee_quat`). 7th dim is gripper
  (line 313 hard-codes `1`).

This is a *very specific* DP setup — pushT-style 2-DOF EE control. Not
6-DOF. **[Kinova-delta]** §6.

### D.2 Sim deployment (sim2sim sanity check)

Same server (`sim_ur_pybullet_apple_interactive`), client uses
`--agent policy` (loads `DiffusionAgent`, `splatsim/agents/policy_agent.py`).
The DP runs on splat-rendered images, environment is splat-render PyBullet.

### D.3 Real deployment

Architecturally identical: just swap the server.

```
Terminal 1: python scripts/launch_nodes.py --robot ur --robot_ip 192.168.1.10
            ┌── splatsim/robots/ur.py::URRobot wraps RTDE
            └── ZMQServerRobot wraps it (launch_nodes.py:223)

Terminal 2: python scripts/launch_camera_nodes.py
            ┌── ZMQ camera server, RealSense D455
Terminal 3: python scripts/launch_camera_clients.py
            └── exposes wrist_rgb, base_rgb to the env

Terminal 4: python scripts/run_env.py --agent policy
            └── identical agent code as sim — the RGBs now come from the real cams
```

Same `obs` dict shape, same `env.step(action)` contract.
This is the entire payoff of the architecture: there is one `agent.act(obs)`
that runs unchanged on either side because both sides serve the same dict.

## 6. **[Kinova-delta]** What does NOT translate to your stack

This is the part you actually care about. Each item is a thing SplatSim
assumes that breaks in our setup, and what we'd do instead.

### 6.1 PyBullet vs. mjlab/MuJoCo

SplatSim's whole runtime is PyBullet. You're on mjlab + MuJoCo with
GPU-batched envs (`pick_cube_distill_osc.py`).

**Implications:**
- We will not be using `splatsim/robots/sim_robot_pybullet_*.py` directly.
- We need MuJoCo equivalents of:
  - per-link world-pose readout (mjlab already provides this — link poses
    are in `data.xpos` / `data.xmat`).
  - object pose readout (also already provided).
- The renderer (`gaussian_renderer.render` from
  `submodules/gaussian-splatting-wrapper`) is **physics-engine-agnostic** —
  it just takes a `GaussianModel` and a `Camera`. So we keep it as-is and
  feed it MuJoCo-derived FKs.

### 6.2 Single env vs. parallel envs

Distillation throughput in your current pipeline relies on hundreds of
parallel envs. Per-env 3DGS rendering at full image res is ≥10ms on a 3080
class GPU per camera; on A6000 you might hit 5–8ms. Two cameras × 256 envs
× 1000 steps becomes a multi-hour cycle.

**Two viable patterns:**
1. **Offline render → cache → train** (SplatSim-style): collect physics-only
   trajectories with mjlab (cheap), then re-render each step through the
   splat *once* and store images on disk. Distillation reads cached images.
   Loses on-line randomization but is fast and matches how SplatSim trains DP.
2. **In-the-loop render with reduced env count**: drop to 16–32 envs, render
   each step. Closer to your current DAgger flow but slower wall-clock.
   Probably best as a Phase-2 experiment after offline-render works.

### 6.3 UR5 URDF + KNN pipeline → Kinova Gen3 URDF

`articulated_robot_pipeline.py` is robot-agnostic *if* you supply:
- Kinova URDF (we already have one in mjlab — but it's a MuJoCo MJCF; the
  pipeline wants URDF for PyBullet's `loadURDF`. We need to either source a
  Kinova URDF or write a URDF→MJCF/PyBullet shim).
- A scan-pose joint-angle list — pick a configuration with the gripper open
  and arm in a workspace-clearing pose (the 90°-everywhere config the README
  recommends doesn't directly apply to a 7-DOF Kinova; pick the closest
  equivalent).
- The fingers of the Robotiq 2F-85 → Kinova gripper mapping is irrelevant for
  us; we use a Kinova-native gripper. The KNN approach itself is
  gripper-agnostic.

### 6.4 Camera intrinsics

SplatSim hard-codes `FoVx = 1.376, FoVy = 1.103` (`get_wrist_camera:710`).
That's an iPhone scan FoV. **We do not want this.** We want the rendered
viewpoint to match the real D455 the deployed policy will see.

Path: read the D455 intrinsics (we already have this in `live_camera/`),
build a `gaussian_splatting.scene.cameras.Camera` with the matching FoVx/FoVy,
and use that at runtime regardless of what the iPhone scan camera was. The
**scan camera and runtime camera do not need to be the same** — the splat is
a 3D representation; we can render from any viewpoint.

### 6.5 Action space

`policy_agent.py` is 2-DOF EE pushT. Your distillation outputs 7-DOF actions
(`pick_cube_distill_osc.py`). We don't want their `DiffusionAgent` —
we want our DAgger student to be the agent. The integration is: at deploy
time, our trained student replaces `DiffusionAgent` and reads the same
{wrist_rgb, base_rgb, state} dict.

### 6.6 Demo collection

We don't have GELLO. We don't need it — our teacher is the trained state-PPO
policy from wandb run `jn3l22j9`. So Stage C is replaced by:
- Roll out the state teacher in mjlab + render through the splat at each
  step. This gives student observations directly, without scripted plans.

## 7. What this implies for our actual port

Here is the sequence we'd need to commit to, in order. **Read this once, then
we discuss and adjust before writing any code.**

```
Phase 0 — Asset capture
  [0.1] Decide: real Kinova workspace or sim-only first?
  [0.2] Capture phone video of the Kinova Gen3 + table + workspace
        (1–2 min, diffuse light, textured background, freeze a known pose).
  [0.3] COLMAP + train 3DGS via the cloned wrapper.
  [0.4] Capture phone video of the cube (the manipuland), 30s, all sides.
        Train a small 3DGS for it.
  [0.5] CloudCompare manual alignment → T_robot_to_splat in objects.yaml.

Phase 1 — Renderer extraction (most work)
  [1.1] Source / write a Kinova Gen3 URDF compatible with PyBullet
        (only needed for the segmentation pipeline; runtime won't use it).
  [1.2] Run articulated_robot_pipeline.py with our robot+joint-states →
        produces data/labels_path/kinova_gen3_labels.npy.
  [1.3] Build a thin standalone module that, given:
          • merged GaussianModel (robot + cube)
          • mjlab link FKs for current joint state
          • mjlab object pose
          • a Camera object with our D455 intrinsics
        returns rendered torch [3,H,W]. Lifted from
        sim_robot_pybullet_base.py:755–880, decoupled from PyBullet.

Phase 2 — mjlab integration
  [2.1] Add a CameraSensor-like custom observation that calls our renderer
        instead of MuJoCo's offscreen renderer.
  [2.2] Decide on offline-render vs. in-the-loop (see §6.2). Recommend
        offline-render for the first end-to-end run.
  [2.3] Add domain randomization on top of splat: lighting (multiplicative
        SH gain), small camera-extrinsic jitter, object-pose noise, distractor
        Gaussians from secondary scans.

Phase 3 — Policy training
  [3.1] Train state-teacher → vision-student DAgger on splat-rendered obs
        (same algorithm as pick_cube_distill_osc.py — only the camera
        observation source changes).
  [3.2] Also train a "control" student on the existing mjlab non-splat
        rendering. Compare side-by-side on real hardware to know whether
        the splat actually buys us anything.

Phase 4 — Real deployment
  [4.1] Drop trained student into nn_policy/sim2real_pick_cube_osc.py
        (vision variant). Real D455 RGBs go in, joint actions come out.
  [4.2] Execute on real Kinova. Iterate on lighting/DR/object scan quality.
```

The **highest-risk steps** are Phase 1 and §6.2 (decide render strategy).
Phase 0 is grunt work but well-defined. Phase 4 is mostly infra you already
have.

## 9. Discussion points before we touch any code

1. **Render strategy** — offline cache vs. in-the-loop. (My recommendation:
   offline first, in-the-loop only if v1 works and we want randomization.)

2. **Where the splat-render module lives in our repo** — propose
   `src/kinova_tasks/sim2real/splat_render.py` as a self-contained module
   the mjlab CameraSensor can call into, rather than mutating mjlab.

3. **Kinova URDF** — do we already have one (PyBullet-loadable) somewhere
   in `src/`, or do we need to build one from MJCF? This blocks Phase 1.2.

4. **Workspace scan scope** — scan just the table+robot, or the whole
   environment including walls? Walls help texture-driven SfM but get baked
   into every rendered frame as a fixed background.

5. **Object randomization** — SplatSim only randomizes the object's *pose*,
   not its *appearance* (because there's only one .ply per object). Are we
   OK with that, or do we want multiple cube-color scans + per-episode
   resampling?

6. **Camera count** — start with both wrist + D455 like the current sim,
   or start with just D455 to halve render cost?
